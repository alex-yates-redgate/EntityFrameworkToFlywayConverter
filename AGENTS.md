# AGENTS.md

Instructions for AI coding agents (and humans in a hurry) working in this repo. [README.md](README.md) explains the project; this file lists what you must not break, and the facts that were learned the hard way.

## What this repo is

A template: developers change an **Entity Framework (EF) Core** model; **Flyway** (Enterprise, run in a container) keeps a schema model and versioned migrations in step, for Ops to deploy. Bash scripts in `Scripts/` connect the two and check they agree.

```
EntityFramework/        EF Core 8 project (C#). Migrations are generated by `dotnet ef`, never hand-edited.
Flyway/                 Flyway project. flyway.toml = shared config. schema-model/ and migrations/ are GENERATED.
Scripts/lib/common.sh   Every shared function and every setting default. Read this before writing a script.
Scripts/*.sh            Entry points (see the table below).
Scripts/docker/flyway/  Dockerfile: redgate/flyway + git.
```

| Script | Purpose | Exit codes |
|---|---|---|
| `DockerDeployFromEntityFrameworkIdempotentScript.sh` | Apply EF migrations to this branch's dev database | 0 ok, 2 can't run |
| `UpdateFlywaySchemaModel.sh` | `flyway diff model`: dev database → `Flyway/schema-model` | 0 ok, 2 can't run |
| `GenerateFlywayMigrations.sh "<desc>"` | `flyway diff generate`: schema model → new `Flyway/migrations/V…`/`U…` (via the shadow database) | 0 ok, 2 can't run |
| `CheckSync.sh [--check NAME]` | Four sync checks: `ef`, `model`, `migrations`, `end-to-end` | 0 in sync, **1 out of sync**, 2 can't run |
| `CheckFlyway.sh [--fail-on-error]` | `flyway check -code` on the migrations | 0 ok, 1 violations (only with flag), 2 can't run |
| `CleanupDatabases.sh` | Drop stale per-branch databases (dry run unless `--yes`) | 0 ok, 2 can't run |
| `SetupDockerOverWSL.sh`, `SetupDotnetPrerequisites.sh` | One-off prerequisite installers for WSL | |

The developer workflow is: change EF model → `dotnet ef migrations add` → **Deploy** → **UpdateFlywaySchemaModel** → **GenerateFlywayMigrations** → **CheckSync** → commit everything together.

## Rules that must not be broken

1. **Never commit `*.user.toml`** (e.g. `Flyway/flyway.user.toml`). It holds per-machine settings and secrets, and must always stay git-ignored. Shared settings go in `flyway.toml`. Before every commit: `git ls-files | grep user.toml` must print nothing. Each Flyway project scopes its own `.gitignore`; don't move those rules to the repo root.
2. **One database naming rule, defined in two places that must agree.** `Scripts/lib/common.sh` (`sanitize_branch_name`, `resolve_database_name`) and `Flyway/flyway.toml` (`${git.branch:ad}` in the `development` and `shadow` URLs). The rule: `<base>_<branch>` (dev database: the EF deploy target *and* Flyway's development database) and `<base>_<branch>_shadow`, where `<branch>` is the git branch with everything except ASCII letters and digits removed. Change one, change the other, and run the end-to-end flow. `CleanupDatabases.sh` also depends on it.
3. **Never edit generated files by hand:** `Flyway/schema-model/**`, `Flyway/migrations/**`, `EntityFramework/Migrations/**`. Regenerate with the scripts. Released migrations are immutable: the scripts only ever add new ones.
4. **Secrets never go on a command line, in `docker inspect`-visible arguments, or into the repo.** Pass them by variable name (`-e NAME`) or via a temp file deleted on exit, as `lib/common.sh` does. For the PoC, `REDGATE_EMAIL`/`REDGATE_TOKEN` and `MSSQL_SA_PASSWORD` come from environment variables, and the scripts print a warning saying so (`_warn_secrets_from_environment`, silenced by `SUPPRESS_SECRETS_WARNING=true`). Before real use they must come from a proper secrets manager: only `require_flyway_auth` and `require_sql_password` should need to change. Keep that warning in place, and keep it on stderr.
5. **Use the plain `docker` CLI only** (via `$DOCKER`). No Docker Desktop, Rancher or Podman specifics, no `docker compose`, no `host.docker.internal`. The customer's engine is unknown by design.
6. **The Flyway image must be `redgate/flyway`** (commercial). `flyway/flyway` is the Community edition and has no `diff`/`model`/`generate`. The version is pinned in one place: `FLYWAY_BASE_IMAGE` in `common.sh`.
7. **Shell scripts use LF line endings** (enforced by `.gitattributes`, as is the Dockerfile). CRLF breaks them in WSL.
8. **Scripts are non-interactive.** Configuration comes from environment variables, results from exit codes, so scripts behave the same for a developer, a git hook and CI. (The two `Setup*` scripts may prompt, with `-y` to skip.)

## Verified facts about Flyway (13.12.2, Enterprise) that are easy to get wrong

- **`flyway diff` exits 0 whether or not it finds differences.** `CheckSync.sh` therefore runs it with `-outputType=json` and counts the entries of the `differences` array (`diff_in_sync` / `summarise_differences`). `CheckSync.sh --output json` gives CI the same result as one JSON document on stdout (progress goes to stderr); keep stdout clean of anything else in that mode.
- **Chained commands need the prefixed options.** `flyway diff model -diff.source=development -diff.target=schemaModel` works; `-source=` only works for a single `diff`. Same for `-diff.buildEnvironment`, `-generate.types`, `-generate.description`.
- **`flyway check -code` needs `-rulesDialect=TSQL`** when there is no database URL. Without it Flyway falls back to ANSI SQL, which parses T-SQL wrongly and misses violations. It exits 0 even with Error violations unless `-check.code.failOnError=true`.
- **The git resolver runs the `git` binary,** which the official image lacks (hence `Scripts/docker/flyway/Dockerfile`). The repo is mounted whole at `/repo` so `.git` is visible, and the Dockerfile sets `safe.directory '*'`.
- **The container must not read the developer's `flyway.user.toml`:** it contains Flyway Desktop `${localSecret…}` placeholders that need a Linux keyring library, and the container crashes on them. `run_flyway` mounts a temporary credentials file over it. Environment-variable credentials do *not* override it.
- **Enterprise activation in a container** works with `FLYWAY_EMAIL` + `FLYWAY_TOKEN` (passed by name). Plain `REDGATE_EMAIL`/`REDGATE_TOKEN` variables are *not* read by the container; `require_flyway_auth` maps them across.
- **Flyway 13 removed `[flyway.check] majorTolerance`.** A config containing it fails to load. Flyway Desktop might re-add it; if `flyway info` fails with "has been removed", that's why.
- `diff … -diff.rebuild=true` works with the shadow environment's `create-database` provisioner: it creates and rebuilds `<db>_shadow`.
- Generated migration names follow `V<n>_<timestamp>__<Description>.sql` (and `U…`), for example `V001_20261118123637__InitialCreation.sql`.

## Other gotchas

- **`localhost,1433` can fail from Windows SQL clients while `127.0.0.1,1433` works** (WSL port forwarding). Flyway URLs use `127.0.0.1`.
- **Windows environment variables don't reach WSL** unless listed in `WSLENV`. The scripts work around that: `import_windows_env` (in `common.sh`) reads an unset variable from the Windows user/machine environment through `powershell.exe`, only under WSL. `require_flyway_auth` and `require_sql_password` call it, so a secret only has to be set in one place. Plain `dotnet ef` run by hand doesn't use that lookup: it needs `MSSQL_SA_PASSWORD/u` in the Windows `WSLENV` (see EndToEndDemoInstructions.md). This is a PoC convenience, like the environment variables themselves: a secrets manager replaces it.
- **`git status` in WSL shows every file modified** on a repo checked out by Windows git (CRLF). It is noise, not a change. Use Windows git, or compare by timestamp.
- EF's unnamed default constraints get auto-generated SQL Server names (like `DF__<Table>__<Column>__398D8EEE`) that can differ between databases with different histories. If a sync check shows a phantom difference on a constraint name, set `ignoreSystemNamedConstraintAndIndexNames = true` in `Flyway/flyway.toml`.
- `EntityFramework/Data/AppDbContextFactory.cs` reads `MSSQL_SA_PASSWORD`, `MSSQL_PORT` and `MSSQL_DATABASE_NAME` for design-time `dotnet ef` commands. Scripts export those before calling `dotnet ef`.

## Conventions for adding or changing a script

Copy the structure of an existing script, for example `CheckFlyway.sh` (short) or `CheckSync.sh` (longer):

1. A **header comment** with `PURPOSE`, `USAGE`, `NEEDS`, `EXIT` (and `CHANGES`/`SETTINGS` where relevant). `--help` prints it.
2. `set -euo pipefail`, then `source "$script_dir/lib/common.sh"`.
3. Call the **preflights you need** (`require_docker`, `require_dotnet_ef`, `require_sql_password`, `require_flyway_auth`) *before* doing any work. They fail with an actionable message.
4. Reuse the helpers (`ensure_sql_container`, `sqlcmd_exec`, `database_exists`, `ensure_flyway_image`, `run_flyway`, `resolve_database_name`, `resolve_flyway_database_name`) rather than calling `docker` directly.
5. Use the exit-code convention: **0** success, **1** a check found a problem, **2** couldn't run (`_fail` does this).
6. New settings: an environment variable with a default in `common.sh` section 1, documented in the README settings table.
7. Mark new scripts executable in git: `git update-index --chmod=+x Scripts/<name>.sh`.

## How to test a change

There is no unit-test suite; verify against real containers (all databases are disposable):

1. `export MSSQL_SA_PASSWORD=… REDGATE_EMAIL=… REDGATE_TOKEN=…`
2. `bash -n Scripts/*.sh Scripts/lib/common.sh` (syntax).
3. Run the real workflow on a scratch branch: add a column to any model class in `EntityFramework/Models/`, `dotnet ef migrations add`, then Deploy → `CheckSync.sh` (expect `model`/`end-to-end` out of sync) → `UpdateFlywaySchemaModel.sh` → `GenerateFlywayMigrations.sh "<desc>"` → `CheckSync.sh` (expect all in sync, exit 0). Then revert the test change and drop the scratch databases with `CleanupDatabases.sh --branch <name> --yes`.

## Troubleshooting a failing `end-to-end` check

Checks 1–3 pass but 4 fails: the Flyway migrations don't reproduce the dev database although each layer matches its neighbour. Likely causes, in order: a filter (`Flyway/Filter.scpf`) hiding objects in one comparison but not another; a Flyway compare option (`[redgateCompare…]` in `flyway.toml`) such as the system-named-constraint option above; or objects EF creates that the schema model excludes. Run `flyway diffText` on the failing comparison (via `run_flyway`) to see the differing definitions.
